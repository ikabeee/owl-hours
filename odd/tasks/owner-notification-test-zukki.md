# Push notification + Test Zukki

Objective: the owner's lock-screen push opens the request (or its decline sheet), and the owner can test Zukki's answers from the Business tab.
Branch: `feat/owner-notification-test-zukki` (worktree `../owl-hours-worktrees/owner-notification`), base `788356f` (fast-forwarded from `67ca98d`, L3). Delivery: `ask-on-risk`. Runner: `node --test` (`npm test -w @owl-hours/owner` via turbo), plus `npm run typecheck`.

## Specs

Sources: `handoff-ui/owner-app/HANDOFF-RN-UI.md` §7 (l.246-283), push spec l.374-378, Test Zukki l.448-454; design HTML `OwNotification.dc.html`, `OwDecline.dc.html`, `OwTestZukki.dc.html`. Copy is taken verbatim from the HTML into `copys/`, never invented.

- **S1 — Decline sheet (OwDecline).** On `request/[id]`, Decline opens a `BottomSheet` inside the same DOM screen with a `RadioList` titled "Why are you declining?" and options "I'm busy right now", "Too far", "Not a service we offer", "Other"; the note "Zukki offers the request to another business right away. The customer won't see your reason."; buttons "Cancel" (closes the sheet, nothing declined) and "Decline request" (destructive). Owl `failed` at 0.4, clipped (§6 l.233). "Decline request" calls `offersService.decline(id, reason)` with the chosen reason, then goes back to Requests, where the item reads "Declined" (l.277). Strings and layout from `OwDecline.dc.html`.
- **S2 — `?decline=1`.** Opening `request/[id]?decline=1` shows the request with the decline sheet already open (l.274). Without the param the sheet starts closed.
- **S3 — Notification response → route.** A pure function maps a notification response to a route: the default tap and the "Open" action go to `request/[id]`; the "Decline" action goes to `request/[id]?decline=1`. A response without a request id maps to no navigation. `app/_layout.tsx` owns the handler (l.246), including the response that cold-started the app.
- **S4 — Notification content and channel.** Uses `expo-notifications` (l.374-378). Title "Urgent: leaking toilet, 1.2 km", body "Water is spreading. Accept within 5 minutes or Zukki offers it to another business." (from `OwNotification.dc.html` l.28, built from the request data, not hardcoded), the request's video thumbnail as the image, actions "Open" and "Decline", Android high-importance channel "Urgent requests". The notification is a remote push sent by the API (S10); the app registers the category with the "Open" and "Decline" actions so the push shows them. User decision (L3): "Full remote push".
- **S5 — Test Zukki screen (OwTestZukki) at `business/test`.** Header: Back (44×44, `aria-label="Back"`, back to Business), title "Test Zukki", subtitle "Only you see this". Intro with owl `idle` (static under reduced motion): "Ask what a customer would ask. Zukki answers with your profile, prices and hours. Customers never see this chat." Owner questions as right bubbles; each answer as a left bubble tagged "Zukki would answer", with its source line ("From: Visit · Night fee · Unclog a drain" + "Edit prices") or "Not in your services" + "Add a service"; both links go to `business/prices`. Composer: input with placeholder and aria-label "Ask like a customer", round "Send" button (44px). Strings and layout from `OwTestZukki.dc.html`.
- **S6 — Test Zukki data.** `testZukkiService.ask(question, history)` returns a domain answer `{ text, sources: string[] }`; an empty `sources` renders "Not in your services". The demo fake client answers from `shared/data/mock.ts` (the two design exchanges reproduce verbatim: the kitchen-sink question and the gas-heater question). The live client calls `POST /v1/owner/test-zukki` (`apps/api/src/routes/v1-owner.ts:116`) with `question` and `history`. API (user decision L3, "API returns sources"): the response adds `sources: string[]`, keeping `businessId` and `reply` unchanged; `sources` holds the `item` of every price rule the price tool returned while answering that question, without duplicates, in first-returned order. Assumption: profile-only answers (hours, area) return no price items, so they also show "Not in your services". Nothing is ever sent to a customer (l.448-454). A failed ask shows an error state with retry, the question stays in the input.
- **S7 — Business row.** The Business tab row "Test Zukki" (`app/(tabs)/business/index.tsx:33`, today a no-op) navigates to `business/test`.
- **S8 — Shared UI rules** (`handoff-ui/HANDOFF-UI.md` l.55, 63): buttons 48px tall, hit areas ≥ 44px, body ≥ 16px, one primary action per screen, works at 130% font size.
- **S9 — Push token registration.** In live mode, "Allow notifications" on onboarding `live` asks the OS for permission (replacing `requestNotificationPermissionStub` in `app/onboarding/live.tsx`). When permission is granted and the owner has a session, the app gets the Expo push token (`getExpoPushTokenAsync` with the EAS `projectId`) and sends it to a new owner API endpoint that upserts `push_tokens (user_id, expo_token, platform)` for the signed-in user (`supabase/migrations/20261028105240_core_schema.sql:338`). Later launches with a session send the token again. Demo mode asks for permission but registers no token. Remote push needs a development build, not Expo Go (https://docs.expo.dev/push-notifications/push-notifications-setup/).
- **S10 — API push sender.** When a request is offered to a business (`connectBusiness`, `apps/api/src/services/whatsapp-service.ts:201`), the API sends an Expo push (https://docs.expo.dev/push-notifications/sending-notifications/) to every token of that business's owners with the request category, the request id in `data`, the S4 title and body built from the request, and Android channel "Urgent requests". Assumption: non-urgent requests use "Accept within 30 minutes or Zukki offers it to another business." and their first sentence comes from the request summary.
- **S11 — Push failures and privacy.** A push failure never blocks or rolls back the offer: the offer and its timer stand, and the failure is logged. Tokens Expo reports as `DeviceNotRegistered` are deleted. Only owners of the offered business get the push (tenant isolation); it carries the approximate distance only, never the address.
- **S12 — Docs and handoff retirement.** `docs/DECISIONS.md` records the push design (token endpoint, sender, failure handling), the `sources` field and the decline reason. In the same PR, the replaced handoff pairs are deleted (AGENTS.md "Handoff retirement rule"): `OwTestZukki`, `OwNotification`, `OwDecline` (`handoff-ui/owner-app/design/html/*.dc.html` and `design/screens/*.png`), once nothing else references them.
